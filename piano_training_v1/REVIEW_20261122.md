## P0停止すると演奏データが消え、採点が常に0点になる

実機で確認した再現手順：

1. 待機モードでバッハを弾く（PERFECT が積み上がり精度100%になる）
2. 「■ 停止」を押す
3. 「★ 採点・講評」を開く
4. → 「0/128ヒット、総合スコア 0/100、ランクD、5軸すべて0」と表示される

「弾き終わる → 停止 → 採点を見る」は最も自然な利用導線であり、この導線では**何をどう弾いても必ず0点**になる。一方、一時停止のまま採点を開くと記録が保持され正しく採点される（実機で 3/128ヒット・54点等の表示を確認）。採点ロジック自体は正常で、停止時のデータ破棄が原因。

### 修正プロンプト

```
「■ 停止」を押しても、そのセッションの演奏記録（ヒット数・判定履歴・タイミング偏差）を破棄しないよう修正してください。
- 停止後に「★ 採点・講評」を開いたら、停止直前の演奏に対する採点が表示されること
- 演奏記録のリセットは「曲を切り替えたとき」と「新たに練習開始を押したとき」だけに限定すること
- あわせて、曲の最終小節まで弾き切った場合は、停止操作なしで採点モーダルへ誘導する（または自動表示する）導線を追加すること
- 修正後、待機モードで数音弾いてから停止→採点を開き、0点でないこと、一時停止→採点の結果と矛盾しないことを確認すること
```

## P1 カウントイン中の打鍵が「WRONG KEY」になる

実機で確認：練習開始直後のカウントイン表示（「準備 2」等）の間に正解の鍵盤を弾いても「WRONG KEY」扱いになる。弾き始めるタイミングが少し早いだけで誤判定され、特に実時間採点では理不尽な減点になる。

### 修正プロンプト

```
カウントイン中（「準備」カウント表示中）の打鍵は、判定対象から除外してください（WRONG KEY にも MISS にも数えない）。
- 待機モード・実時間採点モードの両方で、カウントイン完了後に初めて判定を開始すること
- カウントイン中に弾かれた音は、視覚フィードバック（鍵盤ハイライトと発音）だけ行い、採点データに記録しないこと
```

## P2 鍵盤は49鍵（C3〜C7）— 音域の制約を明記すべき

実機で確認：描画される鍵盤は 88鍵（A0〜C8）ではなく **49鍵（C3〜C7、白鍵29・黒鍵20）**。同梱のマスターAIプロンプト文面にも「4オクターブ（C3〜C7）」とあり意図した設計とみられるが、画面上どこにも音域の制約が表示されていない。現行6曲の音符は範囲内に収まっている（静的確認でリテラル音符は MIDI 66〜84）が、今後低音・高音を使う曲を追加すると、弾けない音・表示されない音が出る。

### 修正プロンプト

```
鍵盤が49鍵（C3〜C7）である制約を、利用者に分かるよう画面上に明記してください（例：鍵盤エリア付近に「対応音域 C3〜C7」の小さな表示）。
あわせて、曲データ読み込み時に音域外の音符が含まれていたら、その音符を音域内へ移高するか、警告を表示するガード処理を追加してください。
将来の拡張として、画面幅に余裕があるPC表示では61鍵（C2〜C7）等への拡大も検討してください（必須ではありません）。
```

## P3 全曲が抜粋（4〜8小節）なのに「全曲」に見える表記がある

静的確認：各曲の小節数は バッハ8／ベートーヴェン8／ショパン6／サティ8／ドビュッシー6／ハノン4。すべて抜粋・一部のみの収録である。ドビュッシーだけ「月の光（冒頭フレーズ）」と明記されているが、ベートーヴェンは「ピアノソナタ第14番『月光』第1楽章」と全曲に見える表記で、利用者が「短い」と感じる食い違いが起きる。

### 修正プロンプト

```
全曲が抜粋収録であることを表記で統一してください。
- 曲セレクターと曲情報エリアで、各曲に「抜粋（全○小節中 ○小節）」等の表記を付けること
- ドビュッシー「（冒頭フレーズ）」のような部分表記がある曲は、形式を全曲で揃えること
- 曲の長さそのものは現状維持でよい（表記の正直さの修正が目的）
```

## P4 CDN依存が強く、読み込み失敗時のガードがない

静的確認：

- Tailwind CSS は Play CDN（`cdn.tailwindcss.com`）経由。本番運用は公式にも非推奨で、表示崩れ・速度のリスクがある
- Tone.js（`cdnjs.cloudflare.com`）に SRI（integrity）が付いていない
- ピアノ音源 Salamander のサンプルは `tonejs.github.io` の外部ホスティング依存。この配信が止まると音が出なくなる
- `typeof Tone` のような読み込み失敗ガードがなく、CDN障害時はアプリ全体が無言で動かなくなる可能性がある

### 修正プロンプト

```
外部CDN依存のリスクを下げてください。
1. Tone.js の script タグに SRI（integrity 属性）を付けること
2. Tone.js の読み込みに失敗した場合に備え、typeof Tone === 'undefined' のチェックを追加し、失敗時は「音源ライブラリの読み込みに失敗しました。再読み込みしてください」とトースト/モーダルで明示すること（無言で止まらないこと）
3. Salamander 音源の読み込み失敗時も同様に、失敗を検知して利用者に知らせること。可能ならフォールバック音源（簡易シンセ）に切り替えること
4. Tailwind Play CDN は、可能ならビルド済みCSSへの置き換えを検討すること（単一HTML構成を維持する場合は、生成済みCSSを style タグへ埋め込む形でもよい）
```

## P5 Gemini APIキーを localStorage に平文保存している

静的確認：APIキーは `localStorage` の `virtuoso_gemini_api_key` に平文で保存され、ブラウザから Google API へ直接送信される設計。単一HTMLのローカルツールとしては一般的な方式だが、`innerHTML` の使用が13箇所あり、万一XSSが混入するとキーが漏洩しうる。利用者への注意喚起も設定画面に見当たらない。

### 修正プロンプト

```
APIキー保存まわりの安全性と説明を改善してください。
1. 設定モーダルに「キーはこのブラウザ内にのみ保存されます。共用PCでは使用後に削除してください」という注意書きを追加すること
2. innerHTML へ代入している13箇所を棚卸しし、外部由来・ユーザー由来の文字列が混入する箇所は textContent への置き換え、またはエスケープ処理を行うこと
3. 「キーを削除」ボタンの動作（localStorage から実際に消えること）を再確認し、削除後にドット表示が未設定状態へ戻ること
```

## P6 ズーム禁止とアクセシビリティ

静的確認：viewport が `maximum-scale=1.0, user-scalable=no` でズーム禁止。`aria-label` は0件、鍵盤やボタンにスクリーンリーダー向けの名前がない。ピアノ練習アプリとしてタップ誤爆防止の意図は理解できるが、視認性が必要な利用者には負担になる。

### 修正プロンプト

```
アクセシビリティを改善してください。
1. viewport の user-scalable=no と maximum-scale=1.0 を外し、ピンチズームを許可すること（鍵盤のマルチタッチ操作と競合しないことを実機で確認すること。競合する場合は、鍵盤エリアのみ touch-action で制御し、ページ全体のズームは許可すること）
2. 主要ボタン（再生・停止・模範演奏・採点・モード切替）に aria-label を付けること
3. 鍵盤の各キーに role="button" と音名の aria-label（例：「C4 ド」）を付けること
```

### 修正プロンプト

```
head に以下を追加してください。

```
