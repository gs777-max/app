# ゴルフ場検索 Webアプリ 設計書

他のAI（または将来の担当）が、このWebアプリの作成・改修を引き継ぐための設計書。
**保守ルール：アプリの仕様・条件項目・表示ルール・デザイン方針に変更があった場合は、本書を都度更新すること（変更履歴に1行追加）。**
関連文書： `ゴルフ場定期選定_引継設計書.md`（定期サーチの共通ルール。本アプリの表示ルールとは一部異なる点があるので第6節を参照）

## 1. 目的・対象

- 不特定のユーザーが、**指定した日付**に、**指定した条件**で、**複数サイト横断**でゴルフ場・プランを探せるWebアプリ。
- アプリは予約をしない。条件に合うプランと、そのプランを実際に予約できるページへのリンクを示すところまで。
- 対応環境： スマートフォン / Windows / Mac（ブラウザのみで動作。インストール不要。レスポンシブ対応）。

### 3.3 予約サイトの検索項目の取り込み（2026-11-11 追加、添付資料2〜9）

ユーザーが提示した主要予約サイト（楽天GORA系／GDO系／詳細検索モーダル）の絞り込み項目を**すべて取り込み、重複は1項目に統一**した。配置は使用頻度で分ける：

**常時表示（基本条件）**： 予約タイプ（通常予約／1人予約／withGolf）、プレー日＋日数（〜N日分）、人数、エリア、出発地点＋車の所要時間、料金（下限〜上限）、スタート時間（時台チップ：〜6時台／7／8／9／10／11時台〜）、保証（2B／3B／一人予約／割増なし）、昼食、ホール数、満員のプランを除外、ゴルフ場名（部分一致）、検索サイト

**詳細検索（「もっと条件を詳しく設定する ＞」で開く）**：
- カート・プレー形式： セルフ／キャディ付き／乗用カート／ナビ付きカート／歩きプレー／Cool Cart／乗り入れ可／暑寒対策カート
- ラウンド・プレースタイル： スループレー／午前スルー／午後スルー／0.5Rプレー／1.5R以上／宿泊付／レッスン付／オープンコンペ／ロングランコンペ／コンペプラン／コンペ特典／ナイトゴルフ
- 連続枠： 2枠以上〜8枠以上
- 特典・優待： 早割・早得／得トク1000／予約者グリーンフィ無料／プレゼント／レディース特典／1人目予約者特典／先行予約者優待／女性優待
- 向けプラン： シニア向け／レディース向け／ジュニア向け
- 施設・サービス： 練習場あり／温泉あり／宿泊施設あり／レンタル可／食事バイキング
- 立地： IC近く／駅が近い／クラブバス送迎あり
- 1人予約・開催の絞込み： 開催見込み／既に予約者がいるプランのみ／同伴者不可プランのみ／withGolfプランのみ
- 除外条件： 9Hプレーを除く／レッスンを除く／スループレーを除く／0.5Rプレーを除く（＋キャンセル無料のみ、ショートコース自動除外、除外キーワード）
- コース条件： 最低ヤーデージ

重複統一の例： 「食事付・昼食付」→昼食項目、「2サム保証（2B保証）」→保証項目、「乗用カート付・ナビ付乗用カート」→カート項目、「送迎バス・クラブバス送迎」→立地のクラブバス送迎、「満員のプランは除外・満員プラン除外」→満員除外トグル。

### 3.4 フォーム枠のスクロール（2026-11-11 バグ修正）

- 検索条件パネル（form.panel）は sticky のまま **max-height: calc(100vh - 90px) ＋ overflow-y: auto** とし、枠内でスクロールできるようにする（スマホは max-height: 82vh）。
- 項目が増えても、結果側の画面はフォームに押し潰されない。

### 3.5 結果の並び替えフィルタ（2026-11-11 追加）

- 並び替えセレクトは**結果エリアの上部**に置き、変更すると即座に再表示する（フォーム側には置かない＝重複させない）。
- 選択肢： 条件マッチ順（既定。割安→近い→総距離→難易度）／安い順／車の移動時間が短い順／総距離が長い順／難易度が高い順／スタートが早い順。

## 4. 表示ルール（本アプリ専用）

- **同一サイト×同一コースのプランは最大3つまで表示**する。並びは「最安 → 同額ならスタート時間が遅い順」。
- 4つ以上ある場合は、3つ表示した下に **「その他 N件あり」** と表示する（N＝表示していない件数、数字で明記）。タップで残りを展開できる。
- **結果（コース）の件数は、条件マッチ順の上位5件まで**とする。マッチ順の優先度は (1)割安順 → (2)車の移動時間が短い順 → (3)コース総距離（総ヤーデージ）が長い順 → (4)難易度（コースレート）が高い順。（ユーザー指示、2026-11-11）
- **ただし該当プランが5件を超える場合は、対象コースとプラン名をすべて挙げること。すべて挙げられない場合は「要確認」と明記する。**（ユーザー指示、2026-11-11）アプリでは、上位5件の詳細表示の下に「該当プラン全件リスト」を出し、料金・空きが未検証の間は「要確認」バッジを付ける形で実装する。
- コース単位では、サイトごとに上記を適用する（サイト別最安の比較可能性を保つため）。
- 特別監視コースの該当プランは通常結果と混ぜず「特別監視」枠に分けて表示する。
- **各プランの表示要素（2026-11-11 ユーザー指示）**： ヒットした各プランには、プレー日・スタート時間・対象サイトを必ず表示する。日付は **yyyy/mm/dd形式（曜日付き、例： 2026/12/12（土））** のバッジ、サイトは略称バッジ（楽天GORA→**楽天**、PGM公式→**PGM**、アコーディア公式→**アコーディア**、GDO→**GDO**、じゃらんゴルフ→**じゃらん**、バリューゴルフ→**バリュー**、コース公式→**公式**）で表示する。サイト見出しも略称に統一する。全件リストの各行と上部のサマリー（プレー日）も同じ日付形式にする。
- **0件時の表示（2026-11-11 ユーザー指示）**： 条件に完全一致する結果が0件の場合は、まず「ニアリーイコール」（条件に近い結果）を表示する。ニアリーの許容範囲： 予算超過¥2,000以内／車の時間超過20分以内／昼食・保証・スタート時間・予約タイプの不一致／エリア外（隣接）／詳細条件の不足2項目まで／9H+α（18H指定時）——外れた点は最大3つまでとし、各プランに赤バッジで理由を表示する。並びは「外れた点が少ない順→条件マッチ順」、最大5コース。除外条件に触れるもの・満員プラン・9Hのみプランはニアリーにも出さない。
- ニアリーも0件の場合は、大きな文字で **「検索結果が0件」** と明示し、条件を緩めるクイックアクション（予算+¥2,000／車の時間+15分相当／詳細条件をすべて外す）を付ける。
- 公式サイトがOTAより安い場合は、公式プランに「公式が最安」バッジを付け、両方を表示する。

> 注意： 定期報告（チャット報告）のルールは「同一コース×サイトで1つだけ表示＋他プラン件数を記載」（引継設計書 第6節）であり、**本アプリの3つ表示ルールとは別**。混同しないこと。

## 5. データの扱い（正直な前提）

- 楽天GORA・PGM・アコーディア等に、登録不要で使える公式の検索APIは存在しない。そのため現行版は次の構成とする：
  1. 条件入力 → 各サイトの検索・予約ページへの**正しい導線リンク生成**
  2. 結果ボード： プランを取り込んで（サンプル／手入力／AI検索結果の貼り付け）第4節のルールで整形・比較表示
- サンプルデータは「デモ」と明記し、実在プランと誤認させない。料金・空きは各サイトでの最終確認が必要な旨を常時表示する。
- **予約リンクのURLルール（2026-11-11 ユーザー指摘で追加）**： 「予約へ」ボタンは企業サイトのトップではなく、各運営の**予約システム／公式予約サイト**へリンクする。
  - PGM公式： 公式サイトは `https://www.pacificgolf.co.jp/index.asp`、オンライン予約システムは `https://booking.pacificgolf.co.jp/`。**`https://www.pgm.co.jp/` は企業サイトであり予約リンク先として誤り**（使わない）。
  - 楽天GORA： 予約導線は `https://booking.gora.golf.rakuten.co.jp/` を使う。
  - アコーディア公式： `https://reserve.accordiagolf.com/`（コース一覧へリダイレクトされる予約ドメイン）。
  - 戸田パブリック： golferweb のコース専用ページ（第3節 #15）。
- 天気・日没のみ Open-Meteo（登録不要・無料）から実データを取得する。取得できない場合は概算表示と明記する。

## 7. デザイン方針（AIっぽくしない）

- ゴルフ誌・老舗予約サービスの編集デザインを基準にする： 深いパイングリーン（#0D3B2E）＋クリーム（#F7F4EC）＋ゴールド（#C8A24A）の3色基調。
- **禁止**： 紫〜青のグラデーション、ガラス質カードの乱用、絵文字の多用、丸み過多のバブルUI、AI生成っぽい均一なカード格子。
- 見出しは明朝系セリフ体、本文はゴシック体。余白と罫線で構造を作る。写真的な質感はSVGの等高線（コース地形）モチーフで表現。
- ヒーローは短く（検索フォームが主役）。装飾より情報密度と読みやすさを優先。

## 8. ユーザビリティ方針

- 検索までの操作は3ステップ以内： (1)基本条件は初期表示、(2)こだわり条件は折りたたみ、(3)ボタン1つで結果へスクロール。
- スマホ： タップ対象は最小48px、画面下部に固定の「探す」ボタン、片手で主要操作が完結。
- プリセットチップで過去の典型条件（75分・¥11,000・2B保証 等）をワンタップ入力。
- 結果は「最安バッジ」「日没リスク」など判断材料を先に目立たせ、詳細は後段に置く。
- キーボード操作・十分なコントラスト・フォーカス表示などアクセシビリティの基本を守る。
- 入力途中でも条件は自動保存され、再訪時に復元される。

## 9. 検証手順（更新の都度、必須）

1. 実ブラウザ（Chromium）でファイルを開き、初期表示・プリセット適用・検索（絞り込み）・「その他N件」展開・比較トレイ・AI依頼文コピーを実際に操作する。
2. スマホ幅（例： 390px）とデスクトップ幅の両方でレイアウト崩れがないか確認する。
3. コンソールエラーがないこと、Open-Meteo取得失敗時も画面が壊れないことを確認する。
4. 検証結果（ブラウザ、幅、確認した操作）を報告に含める。ヘッドレスのDOM確認だけで「動作する」と言わない。
