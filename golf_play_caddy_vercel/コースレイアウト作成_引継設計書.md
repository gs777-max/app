## 0. 運用ルール（最重要）

1. **コース作成・改修を行ったら、本書を同時に更新する。** 新しく得た判断材料、コース固有の事情、失敗と対策は、その作業の完了報告までに本書へ反映する（特に第11章「実施済みコースと特殊事情」と第10章「教訓集」、末尾の更新履歴）。
2. 本書とユーザーの最新の明示指示が食い違う場合は、ユーザーの指示が優先する。その場合も、指示内容を本書に記録してから作業する。
3. 本書に書かれていない判断が必要になったら、推測で進めず、第3章の優先順位で判断し、判断根拠を作業フォルダのレポートに残す。

## 3. 判断ルール（情報源の優先順位）

食い違いが起きたときの決定順位（ユーザー決定事項を含む）：

1. **参照元（公式レイアウト図）の配線が正**：線の本数・開始／終了・切れ目は図面どおり。図面が分離している線は絶対に繋がない。
2. **座標は実地形（衛星デジタイズ実測）が正**：図面が模式的に描く位置（池の左右など）は地形に従う。
3. **ヤーデージの矛盾は「実測形状で判定 → 決着しなければ楽天GORA」** の順。公式表同士が違う場合、まずデジタイズした幾何で測り直す（大平台 中2：実測によりアコーディア/GDOの572yを採用、GORAの504yは列ずれとして不採用）。
4. 運営公式（例：アコーディア）のホール別表が一次情報。HDCPは公式を正とし、GORA/golfscaleが食い違う場合は公式を採る（習志野で実証：GORAのHDCPは公式とほぼ全ホール不一致だった）。
5. レーティングはJGA公表値（GORA/golfscale）を登録する。ホール別ヤーデージ合計と一致しないことがあるが、**レーティングは公表値のまま別管理**とし、相違をレポートに明記する（取手：Red公表4,680y vs 公式表合計5,055y等）。
6. 公式にレイアウト情報がないコースは、第7章「戸田型」の代替情報源の格付けに従う。

## 4. 立規則（絶対事項）

1. **配線を先に把握してからプロットする**：図面の各セグメントの開始・終了・切れ目を棚卸ししてから地形へトレースする。例：大平台 東1のグリーン奥OB線は左上で「終わって」おり、左側の線とは接続しない。
2. **境界線は林の輪郭に沿う流線**：直線の組み合わせではなく、地形の縁を密な点列でなぞる（アプリ表示でも滑らかに描かれるよう点列で保存）。スタイルは **Pattern A（標準線＋長い線にはOBラベル）** で統一。
3. **推測でハザードを足さない**：地形で実在が確認できたものだけ登録する。図面総数と実在確認数が違う場合は、確認できた数だけを登録し、差異と理由をレポートに書く（取手：バンカー図面68個中、実在確認54個のみ登録）。
4. **ユーザーデータを消さない**：登録前に必ず既存レコードを取得・バックアップし、保全対象（手動登録・キャリブレーション・IP・ショット・墓標）を棚卸しする。POSTは必要なキーだけ送る（第5.4節のマージ仕様を前提に設計する）。
5. **両IDへ登録する**：アプリは同じコースを「内蔵プリセットID」と「検索ディレクトリID（osm_way_*）」の2つのIDで持ちうる。両方に同一データを登録し、両方とも照合する。
6. **検証ブラウザで本番データを触らない**：検証用ブラウザの操作（ドラッグ等）が実データを書き換えた事故が過去にある（第10章）。検証は読み取り専用の再現環境（API差し替え）で行う。
7. アプリの既存機能「横幅計測」はレイアウト作業と無関係に削除しない（アプリ全体の立規則）。

## 5. データ仕様（SmartCaddie Pro）

### 5.1 コースID

- 内蔵プリセットID：アプリの `index.html` 内プリセット定義の `id`（例：`taiheidai_cc`、`narashino`、`toride`、`toda_public`）。
- 検索ディレクトリID：OSMのコース境界wayのID（例：`osm_way_426701484`）。コース中心座標からOverpassで境界wayを特定する。
- 登録前に両IDのGETを行い、既存データの有無と内容を必ず確認する。

### 5.2 ホールオブジェクト

登録データの `holes` は「選択中の組合せにおけるラウンド位置 h=1..18」の配列。

| フィールド | 内容 |
|---|---|
| `h` | ラウンド位置（1〜18） |
| `sub` / `no` | サブコース名（例「中」）／そのサブコース内のホール番号 |
| `par` / `yard` | 公式Par／既定ティー・既定グリーンでの距離（ルート長。Par3は直線） |
| `tee` / `pin` | 既定ティー／既定ピンの座標 `[lat, lon]` |
| `pinL` / `pinR` | L＝Aグリーン（メイン）、R＝Bグリーン（サブ）の座標。1グリーン制は両方ともグリーン中心と同値 |
| `calibTees` | 全ティーの座標 `{black, blue, white, gold, red}`（存在するティーのみ） |
| `calibPins` | `{L, R}` のピン座標 |
| `savedIps` | IP座標の辞書。キーは `"<tee>_<side>"`（例 `white_L`）。値は `[lat, lon]` の配列 |
| `routePts` | ルート線（フェアウェイ中心線）の `[lat, lon]` 点列。バックティー始点→既定グリーン（L） |
| `routeSource` | ルートの出典メモ（例：`manual-digitized`） |
| `manual: true` / `placeholder: false` | 手動確定データであることの印（placeholderのままだと仮表示扱いになる） |
| `hdcp` | ホール別HDCP |
| `boundaries` | `{ ob: [線の点列, …], penalty: [ポリゴンの点列, …], hazards: [{type: 'bunker'\|'pond', at: [lat, lon]}] }` |

アプリ側のキー対応（localStorage／クラウドのグループ名）：キャリブレーションは `golf_calib_tee_{courseId}_{h}_{teeType}`、`golf_calib_pin_{courseId}_{h}_{greenSide}`（greenSideは `L`/`R`）。IPは `smart_ip_route_*`。**これらは位置（h）キーであり、組合せをまたぐと危険**（第10章）。

### 5.3 組合せ（combos）・レーティング

- 27H・36Hなど組合せがあるコース：トップレベル `holes` ＝代表組合せ（例：中→東）、`combos` に `{ "東→西": {holes: [...]}, "西→中": {...} }` の形で他組合せを入れる。
- 組合せキーはアプリの正規化（サブコース名から「コース」を除去、矢印を `→` に統一、空白除去）に一致させる。
- `ratings` のキーはアプリが実際に読む形式に合わせる：`"<組合せ>|A（ベント）"`、`"<組合せ>|B（高麗）"`（大平台）。1グリーンの取手では `"OUT→IN|ベント"` 形式だった。**登録前にアプリの `wizardRatingRow` 等の読み取りコードでキー形式を確認すること**（推測で決めない）。
- `hdcpChart`：組合せ×グリーンのHDCP表（アプリ表示用）。

### 5.4 サーバー仕様（api/course.js、本番Vercel）

- GET：`/api/course?id=<courseId>` → `{success, courseId, data}`。ヘルスチェックは `?health=1`（`db:"ok"` が正常）。
- POST：`{courseId, ...}` を送る。ボディ上限2MB。
- マージ規則：
  - `holes` 等のトップレベル通常フィールドは、POSTに**含まれる場合のみ全体置換**（含まれないフィールドは保持される）。
  - グループ（`manualHoles` / `calibrations` / `ips`）はエントリ単位で `updatedAt` によりマージ。
  - `deleted`（墓標）はマージされ、対象エントリへ適用される（サーバー保持期間90日）。
  - `updatedAt` はサーバーが打刻。既存レコードは上書き前に `course:<id>:__prev` へ自動バックアップされる。
- よって「holesだけ差し替えてユーザーデータを守る」登録は `{courseId, holes}` のPOSTで実現できる（戸田で実証）。組合せコースは `holes` と `combos` と `ratings` を正規データで送る。

### 5.5 アプリ側の適用仕様と既知の制約

- 取り込み時は `combos[現在の組合せ].holes` が優先適用される（なければトップレベル `holes`）。
- UI状態（ティー／グリーン／ローテーション）の復元は、combos付きレコードでは行われない（v7で修正済み。旧仕様はローテーションを巻き戻すバグだった）。
- ローテーション切替時に未適用の節は自動で取り込まれる（v9で修正済み）。
- 描画：OB＝白線＋暗い縁取り＋長い線にOBラベル、赤ペナルティ＝破線の半透明ポリゴン、バンカー＝砂色の円（半径7m）、池＝青い円（半径12m）。
- 公式テーブルにないティー（例：Greenティー）はアプリID `gold` に対応させる。大平台のGreen＝`gold`。
- 内蔵プリセットの中心座標が実コースからずれていることがある（大平台 約4.8km、習志野 約2.3km、取手 約800mの実績）。**新コースでは必ずプリセット中心と実コース重心を照合し、ずれていればアプリ修正の対象として報告する**（修正はユーザーのコミット承認を得てから）。

## 6. 作業手順の詳細

### Phase 0：準備と保全棚卸し

1. 作業フォルダ `~/workspace/smartcaddie-<course>/` を作る。**大きなファイル（モザイク等）は最初からここに置く**（`/tmp` は容量が小さく再起動で消える）。
2. 両IDのGETを取得し `cloud_record_backup.json` として保存。以下を棚卸しする：
   - `holes`（ユーザーの手動プロットがあるか）、`manualHoles`、`calibrations`、`ips`、`deleted`（墓標）の件数と内容
   - スコア・ショット記録等の有無、UI状態（現在のティー／グリーン／組合せ）
3. 保全方針を決める：原則は「ユーザーの手動データは正として保持し、新規分は不足分を補う」。ユーザーが書き換えを明示許可した場合のみ幾何の是正を行う（戸田の事例。許可の有無をレポート冒頭に明記）。

### Phase 1：公式調査（research_official.md の書式）

以下を必ず含める：
- 基本情報（正式名称、所在地、運営、ホール構成、グリーン種別、設計者）
- 全ホール表：Par、全ティー別ヤーデージ、HDCPを**2ソース以上**（運営公式＋GORA／golfscale／GDO等）で転記
- レーティング（組合せ×グリーン×ティー：レーティング／総距離／スロープ）
- ソース間の相違点リスト（後の判断材料）
- レイアウト図のURL（ホール別図がある場合はホールごとに）
- OSM所見（境界wayのID、ホールレベルの地物が有るか）
- アプリID（プリセットID／ディレクトリID）とプリセット中心座標の照合結果
- 未確定事項リスト

### Phase 2：図面棚卸し

- ホールごとに、図面から先に読み取る：形状（ドッグレッグ方向）、OB線の本数・開始／終了位置・**切れ目**、赤ペナルティの有無と範囲、池・バンカーの図面上の配置。
- この棚卸しが終わるまで座標作業に入らない（立規則1）。

### Phase 3：衛星モザイク

- GSI（国土地理院）seamlessphoto z18 と Esri World Imagery（冬季撮影分が芝の判別に有効）を、コース全域＋余白でモザイク化する。両者は同一タイルグリッドに揃える（z18で約0.483m/px）。
- `mosaic_meta.json` に `{z, x0, y0（タイル原点）, w, h}` を保存。
- `dist.py` に px⇔latlon変換、区間距離（m）、ルート長（yd）、弧長位置の点を返す関数を用意する（既存コースのものを雛形にする）。

### Phase 4：同定

1. ティーグラウンド群とグリーンをモザイク上で同定する。**拡大cropを目視で確認すること（数値の当て推量禁止）**。
2. アンカー＝バックティー。ルート（フェアウェイ中心線のpx点列）をティー→グリーン中心へ引く。
3. 他ティーはルート沿いの弧長で配置する：当該ティーの弧長 ＝ バックティー弧長 −（バック距離 − 当該ティー距離）。ティーグラウンドの実在位置（台地の前後端）と矛盾しないか目視確認する。
4. **A/Bグリーンの判定**：
   - 2グリーン制で芝種が違う場合（ベント／高麗）：冬季画像の芝の明度で判定する（較正実績：Aベント＝暗い 93〜114、B高麗＝明るい 129〜162）。**距離だけで割り当ててはいけない**（大平台で2件の誤判定が出た）。
   - 両グリーンとも同じ芝種の場合（習志野＝両ベント）：明度法は使えない。分岐点モデル（ルートがグリーン手前で分岐する点から両グリーンへの距離差）とティーボックス実測Δの合算スコアで判定し、証拠が割れたホールは contested としてフラグに残す。
   - 判断が割れた項目は、ユーザーに「図面を正とするか」の確認を取ることがある（大平台の6件）。図面優先と決まった項目は、その結果としての距離誤差も含めて記録する。
5. グリーンは全て相異なる面であることを確認する（衝突があれば同定ミス）。予備／練習グリーンを本グリーンと誤認しない。

### Phase 5：境界配線

- OB：図面棚卸しのセグメントどおりに、地形の林縁を密な点列でトレース（ポリライン）。
- 赤ペナルティ：図面にある場合のみ、帯状ポリゴンで登録。
- バンカー／池：地形から中心座標を記録（アプリは円で描画する）。コース公式の総数（バンカー総数・池が絡むホール数）と照合する。
- OSMにフェアウェイポリゴンがあるコースでは、フェアウェイ縁を約6m外側へオフセットした線を基礎にできる（習志野方式）。ただし図面の例外（グリーン奥の接続、池側はOBでなくペナルティ等）を必ず反映する。

### Phase 6：データセット構築

- 構築は再現可能なスクリプト（`build_dataset.py`）で行い、手作業の直接編集をしない。
- IP配置：ドライバー250y想定。ティー×グリーン面ごとに、250y刻みで残り40y超の間配置。Par3には置かない。
- ヤーデージ：`yard` は既定ティー×既定グリーンのルート長。Par3は直線。

### Phase 7：自己検証

- ティー×グリーンの全セルでルート長を公式表と照合し、誤差表を作る。**±18yを目安**とし、超えたセルは理由（公式表の癖／図面優先の結果／同定の不確実性）を明記する。
- 全ティー・グリーン・ルート点がコース境界ポリゴン内にあること、グリーンが全て相異なることを機械チェックする。
- 消去法で割り当てたホール、確度の低い同定は「現地確認候補」として優先順位付きでリスト化する。

### Phase 8：本番登録

1. 登録直前にもう一度GETし、Phase 0のバックアップから変化がないか確認する（他端末の更新を潰さない）。
2. POSTする（第5.4節）。両IDとも。
3. 登録後GETで全項目照合（tee/pinL/pinR/calibTees/calibPins/savedIps/boundaries/ratings/combos）し、**差分ゼロ（ALL CANONICAL）**を確認する。保全対象の件数・内容が不変であることも照合する。

### Phase 9：実画面確認

- 本番コード＋実データのクリーン環境再現（APIを差し替えたローカル実行）で、組合せごと・数ホールの座標解決（距離が公式と一致するか、境界が入っているか）を確認する。
- **検証用ブラウザのプロファイルは共有され、localStorage汚染で誤表示が出る**（第10章）。異常値が出たら、まず汚染を疑い、クリーン環境で再現確認してから判断する。
- 最終判断はユーザーの実機で行う前提とし、実機で必要な操作（「📥 取込」1回など）を報告に含める。

### Phase 10：報告

- 完了報告には必ず含める：登録結果、自己検証の要約（±18y超のセルと理由）、現地確認候補、未解決事項、**サンプル画像2〜3枚**（登録データから衛星画像上に描画したもの）、**情報源URLの一覧**。
- 宿題事項（ユーザー側／アプリ側）を分けて明記する。

## 7. コース類型別の進め方

### 大平台・取手型（OSMにホールデータなし）
- 衛星デジタイズが主体。第6章の手順どおり。図面が公式サイトにある場合は図面優先を徹底する。

### 習志野型（OSMにホールデータが豊富）
- `golf=hole` センターライン、ティー／グリーン／フェアウェイ／バンカーの地物が使える。ただしセンターラインは大会用複合コースの番号付けになっている場合がある（ZOZO複合18H）。ライン名と実ホールの対応は、開始／終了位置と公式ヤーデージで検証してから使う。
- センターラインのないホールは、フェアウェイ回廊の軸線＋ティーボックスの距離フィンガープリント＋グリーン→次ティーの接続チェーン＋公式ガイド文で同定する。

### 戸田型（公式にレイアウト・OB情報がない）
- 情報源の格付け（実績）：GPS機器メーカーのゴルフ場ガイド（Shot Navi等。更新日が新しいもの）＞ 会員のホール別ガイド記事（note等。OB／ペナルティの左右帰属の正として採用可。ただし距離は古い場合があり正にしない）＞ GDO等の図面（ハザード位置の照合用。OB線画がないことがある）。
- 取得できない資料（403等）は、手段を尽くしたうえで「未解決事項」として明記する（推測で埋めない）。
- 9ホールを2周する型は、「物理ホール」と「ラウンド位置（h）」を分けて考える。ティーエリア×グリーンの組合せで18H分を構成し、既定グリーンは公表ヤーデージに最も整合する方を選ぶ。

### 1グリーン制（取手型）
- `pin = pinL = pinR =` グリーン中心、`calibPins {L, R}` は同値、`savedIps` は `<tee>_L` と `<tee>_R` の両方に同値を入れる（R表示でもIPが出るようにするためのアプリ仕様対応）。

## 10. 教訓集（事故・失敗と対策）

1. **位置キーの汚染（2026-11-08、大平台）**：検証セッションが残した位置キー（`smart_ip_route_*`、`golf_calib_*`）の古い上書きが、ローテーションをまたいで別のホールに表示された。対策：正規データを全セクション再POSTし、古いキーは墓標で掃除。**位置キーはローテーション非安全**という前提で照合する。
2. **検証ブラウザのドラッグ事故（同日）**：確認操作中にIPマーカーをドラッグしてしまい、本番に一時保存された。対策：第4章・立規則6（検証はAPI差し替えの再現環境で、実データに触れない）。
3. **UI状態の復元バグ（v7で修正）**：取込時にクラウド保存済みのローテーションがウィザードの選択を上書きし、混在状態の保存（＝事故1の遠因）になった。combos付きではUI状態を復元しない仕様に修正済み。
4. **ローテーション切替で仮表示のまま（v9で修正）**：同一端末で組合せを切り替えると、同期判定が「変化なし」となり新しい組合せが仮表示のままだった。現在の組合せの節がクラウドにあり画面が仮表示なら取り込む仕様に修正済み。
5. **距離だけでA/Bを割り当てて誤判定（大平台 東4・東8）**：2グリーン制のA/B判定は芝の明度（またはフィッティング）で行い、距離のみで決めない。
6. **Shot Naviのホール別図面画像が全経路403（戸田）**：直接・ブラウザ・Waybackすべて不可だった。取得不能は未解決として明記し、代替情報源（距離表・全体図・文章ガイド）で構成する。推測で線を引かない。
7. **プリセット中心座標のずれ（3コース連続）**：大平台・習志野・取手すべてで内蔵プリセットの中心が実コースからずれていた。新コースでは必ず照合する（チェックリストに含む）。
8. **`/tmp` は消える・小さい**：大きなファイルは最初から作業フォルダへ。モザイクやインストーラを `/tmp` に置かない。
9. **並行同定ではグリーンが二重に主張される（潮来、2026-11-14）**：9ホール単位で並行に同定すると、別担当が同じグリーン面を別ホールに割り当てる（潮来では南クラスターで4か所の衝突＋3面不足）。対策：同定のあと必ずクラスター単位の照合パスを入れ、全グリーンの一意性（27面がすべて相異なること）を機械チェックしてからビルドする。照合では「グリーン→次ティーの歩行距離」も見る（不自然に長い歩行は誤割当ての兆候）。
10. **練習グリーンとの取り違え（潮来 OUT H7、2026-11-14）**：クラブハウス近くの練習グリーンは本グリーンそっくりに見える（白いカバー付きオーバル、バンカーなし）。対策：クラブハウスに近いオーバルは練習グリーンを疑い、バンカー配置・ガイド文（池越え等）・ヤーデージの3点で照合する。
11. **図面のオレンジ線（ペナルティ線）の有無はペナルティの有無と等しくない（潮来、2026-11-14）**：じゃらん図の線は描き方が不統一（線なし6ホール、池があっても線なし7ホール以上、切れ目6か所）。対策：池ごとに地形で判定し、線がなくても水域ならペナルティ、線があっても地形が伴わなければ付けない。判断はホールごとに記録する。
12. **赤ペナルティのポリゴンは水面＋約12mに絞る（潮来、2026-11-14）**：粗く描くとフェアウェイまで赤く染まり、画面上で「フェアウェイがペナルティ内」に見える。対策：水際を密な点列でなぞり、余白は約12mまで。共有池は両ホールに同一ポリゴンを入れてよい（潮来 SOUTH H4/H5）。
13. **モザイク取得スクリプトはタイル用ディレクトリを作らない（潮来、2026-11-14）**：取手の `download_mosaics.py` は `tiles_gsi/` / `tiles_esri/` の作成をせず、初回実行では全タイルが無言で失敗する。対策：スクリプト先頭で `os.makedirs(..., exist_ok=True)` する（今後のコース用テンプレートに反映）。
9. **クロスコースのグリーン競合（2026-11-14、キャスコ花葉）**：隣接する3コースで同じグリーンを2コースが主張した（G4＝シバザクラH8 vs サルビアH9）。解決は「証拠の強さ」で決める（サルビア側：ティー群＋全ティー±3y＋H9 Black −21y）。敗れた側は代替グリーンを衛星ズームで実確認して再割当てする（シバザクラH8→G5、ルート434.5y/+0.5y）。**グリーンの帰属はコース横断で照合する**（1コースだけ見ていると気づかない）。
10. **OSMホール中心線が最強のアンカー（2026-11-14、キャスコ花葉リンドウH9）**：OSM way 923012888 の3点 (3432,2747)→(2905,2541)→P1(2753,2226) が公式484yと0.0y一致し、H9を確定させた。OSMのティー2基も同位置。**OSMに中心線があるホールはまずそれを採用し、他ホールの割当てはそのアンカーに合わせる**。
11. **公式マップは様式化・異方性伸縮（2026-11-14、キャスコ花葉）**：公式全体図は位置・方向には使えない（長軸・短軸の縮尺が違い、ICPフィットも不成立）。トポロジー（パー／ドッグレッグ方向／ホール順）と解説文のみ参照し、位置は衛星フェアウェイ＋ヤーデージで決める。**マップの「上下左右」を衛星の東西南北に直読しない**。
12. **OSM rough ポリゴン長はティー→グリーン距離を過大評価する（2026-11-14、霞台筑波OUT）**：rough ポリゴンの PCA extent はティー・グリーンを越えて広がるため、extent（例：96824140 は 341y）に対しティー→グリーン直線は 283y と 60y 近く短いことがある。ヤーデージ照合は extent ではなく**ティー→重心→グリーン（分岐点モデル）**で行うこと。extent だけでのホール割当ては誤る。
13. **GSI モザイクは ESRI より池・フェアウェイの判読性が高い（2026-11-14、霞台筑波OUT H6）**：H6 の横断池は ESRI では判読しづらく GSI で確定した。池の同定は ESRI だけで諦めず、GSI でも確認すること。
14. **分岐点モデルの L≠R ホールは R 誤差＝公式Δ が出る（2026-11-14、霞台筑波OUT H6）**：重心が pinL・pinR の中点のため両脚が等しく、モデル R 距離＝公式 R 値となり、公式 L 値との差（H6 Blue 19y）がそのまま R 誤差として出る。霞コース H11（R 誤差 +12.0）と同じ既知の特性であり、異常ではない。A/B の真の検証はティーボックスからの直線実測Δ（H6 はモザイク直線で 9y、公式 19y）で行う。
15. **検出グリーンの「ペア」が隣接2ホールのグリーンである場合がある（2026-11-14、霞台筑波OUT A03）**：A03 の2面は H4 とパー3廊下 96825261 のグリーンだった。ペアはフェアウェイ方向で検証すること。**アイランドグリーンがモザイクで見つからない場合は contested として残し、無理に割り当てない**（筑波OUT H3 は ESRI・GSI・OSM・全候補池を除外し、未発見のまま contested）。
16. **36Hインターリーブ敷地ではコース間のグリーン重複を機械チェックする（2026-11-14、霞台）**：各担当の「18面相異なる」はコース内のみで、筑波OUT H9＝筑波IN H13 が 1.1m で同一グリーンになる等、コース間・担当間で6件の衝突が発生した。対策：同定のあと必ず突き合わせフェーズを入れ、全72ピンの pairwise 距離を機械チェックし、40m未満のペアを1件ずつ目視で解消する。衝突の解消には Accordia図の形状＋じゃらん衛星図＋廊下の連続性を使う。
17. **島グリーンを別コースのピンにしない（2026-11-14、霞台 霞H11）**：霞H11のピンが筑波OUT H3の島グリーンを指す誤同定があった（島グリーンは目立つため引き寄せられやすい）。対策：突き合わせで全ピンの帰属を確認し、島グリーン・目立つグリーンは「どのホールのものか」を図面と廊下で裏付けてから採用する。霞H11は陸上ペア (7237,2737)/(7312,2862)（三角バンカー・小川・池がAccordia 4_2と一致）へ再同定した。
18. **組合せキーとレーティングキーはアプリ実コードで検証する（2026-11-15、霞台）**：`currentComboKey()` の正規化（「コース」除去、「➔」→「→」、空白除去）を読み、「筑波コース ⇔ 霞コース」→ `筑波⇔霞`、「霞コース ⇔ 筑波コース」→ `霞⇔筑波` を確認してからペイロードを組んだ（⇔は置換対象外）。ratingsキーも同じ正規化で `筑波⇔霞|A（ベント）` 等とした。**混合ローテーションのティー別レーティングは公表されていないため、フルコース値（筑波メイン黒 72.4等）を回転キーに付けない**（付けるとウィザードに誤表示される）。登録したのは GDO／KGA の混合バック 70.9（Blackのみ、ヤード・スロープなし）だけ。未検証のスロープも付けない（白・霞メイン124のみ公表）。
19. **combos エントリは必ず `{holes: [...]}` のオブジェクト形にする。裸のリストは禁止（2026-11-15、キャスコ花葉）**：登録ペイロードで combos を `{holes: [...]}` にせずホール配列そのままを値に入れたため、アプリは `combos[key].holes` を読めず（裸のリストでは undefined）、該当の回転（リンドウ⇔サルビア／シバザクラ⇔サルビア）はプレースホルダー表示（「位置データ未取得」、H1 の 510y を繰り返し、線なし）になった。トップレベル（リンドウ⇔シバザクラ）は combos ではなく top-level holes のため正常表示で、気づきにくい。対策：①登録前にペイロードの combos が全て `{holes: [...]}` 形であることを assert する（検証スクリプトの裸リスト許容の分岐を削除する）。②潮来・霞台はオブジェクト形で登録済み（キャスコのみ裸リストだった）ため、新規コースでは必ずオブジェクト形を確認する。③修正は `{courseId, combos}` のみの POST で行い（holes は送らない。サーバーは combos を全体置換し、holes は保持する）、修正前後で GET-diff を取り、全ホール項目・トップレベル・ratings・groups が不変であることを確認する。
